  and `expired`. Recorded as A9 in decisions.md.

  provider's job list, the `counter_lapsed` text).

- Breaking? No: same status code and error code; the offer ends `lapsed` instead of staying

## 4. Scheduling: long first visits and the four-week fallback (bug)
- What: `app/services/schedule.first_slot`. (a) A first visit longer than its window never
  fits (a first regular clean is 240 minutes; the morning window is 09:00 to 12:00), so
  every day is skipped; (b) the fallback after four weeks then books tomorrow at 09:00
  without checking the provider's working days, the customer's days or time off. In the L1
  walk-through, two weekday-only requests booked with providers who don't work Sundays got
  "Sunday 4 October, morning".
- Suggested fix: let a visit start at the window's start when the day is otherwise free even
  if it runs past the window's end, and make the fallback the first day that passes the
  same working-day, customer-day and time-off checks.
- Workaround now: none in L1 (the booking is created by the shared service).
- Breaking? No. Affects L1 (booking screens) and L2 (Today's round).
- **Status (session S): resolved** in `ba57828` (A14): a visit longer than its window starts at the window's start on a day with room; the search runs six months and never picks a day the provider doesn't work or is away. Tests for weekday-only cleaning and flat-pack bookings.

## 15. One charging path: tips go through `app.payments.charging` (done, at Hasan's instruction)
- What: L1's rating no longer charges the tip itself. The rating commits with the tip amount, then
  `app.payments.charging.charge_visit(db, s, gateway, visit_id, purpose="tip")` records the intent,
  calls the gateway outside any transaction with the attempt's idempotency key
  (`visit:<id>:tip`) and records the result with the ledger tip entry. L3's
  `settle_pending_payments` task already settles pending tip charges, so L1's own settle step and
  its `tip_reconcile` task are removed. Two small additions in L3's package: `notices.tip_paid`
  and its template `tip_received` (registered in `app/payments/notices.py`), sent from
  `charging.apply_result` when a tip succeeds, so the provider hears of the tip exactly once
  whichever path records it (the request, a webhook, the settle task). `rating_received` no longer
  mentions a tip (it's sent before the tip is charged).
- Recovery (Codex review): if a request stops after the rating commits but before the tip's charge
  intent exists, a retry of the rating starts the charge, and L1's `orphaned_tips` task starts any
  that nobody retried (after two minutes). Safe because the gateway is only called once an intent
  is recorded. L3's `settle_pending_payments` could take this over (tips with `tip_pence > 0` and no
  `tip_charge`) if integration prefers one task.
- Why: one charging path (Hasan).
- Breaking? No. `RatingOut.tip_status` can also be `pending` (outcome not known yet).
- **Status (session S): resolved.** Done by L1. Declined: folding `orphaned_tips` into L3's `settle_pending_payments`: both are safe (the gateway is only called once an intent exists) and merging them changes nothing a customer or provider sees.

## 19. Make the horizon top-up transactional (F; raised by Codex, not fixed in L1)
- What: `app/shared/tasks.top_up_series` reads every active plan at the start of its loop and calls
  `schedule.ensure_horizon` with that copy, outside any transaction. If a plan changes while the
  loop runs (a change of frequency accepted under A10, a pause, a cancellation), the task can still
  insert a visit at the old cadence and price after the change commits. Fix: for each plan, run
  `transaction(db, fn)` where `fn` re-reads the series (and its provider and booking) with the
  session, returns if it isn't active, and calls `ensure_horizon(..., session=session)`;
  `ensure_horizon` already writes `horizon_until` on the series whenever it adds dates, so a
  concurrent plan change conflicts and the re-run sees it.
- Why: Codex (high) on L1's A10. The race was already there for pauses and cancellation; A10
  makes it able to leave a visit at an old price. The window is one series' turn in the hourly
  loop.
- Workaround now: none in L1 (F-owned task and service; you sent foundation items to the
  shared-fixes session). L1's own writes are transactional.
- Breaking? No.
- **Status (session S): resolved** in `ba57828` (A13): `schedule.top_up` runs each plan in its own transaction on the plan as it is now; L2's time-off look-ahead uses it too.
