# Contract-change requests from L3

See README.md for the format. All additive unless marked otherwise.

## PaymentGateway: additions and an optional field
- What: `app/adapters/payments/base.py` (L3-owned, but other lanes call it):
  - `refund(..., idempotency_key: str | None = None)`: an optional keyword; a repeat with the same
    key returns the same refund. `RefundResult.status` now describes the customer's refund only
    (`pending` includes "outcome unknown", with no refund id); our fee goes back only once it has
    succeeded (`fee_refunded_pence`).
  - `refund_status(refund_id) -> RefundResult` and
    `refund_fee(charge_id, fee_refund_pence, *, idempotency_key) -> RefundResult`: read a refund
    without making it again, and return the fee part separately.
  - `charge_status(payment_intent_id) -> ChargeResult` and
    `cancel_charge(payment_intent_id) -> ChargeResult`: read an attempt, and cancel one that hasn't
    succeeded so a retry can't leave two payments open.
  - `find_charge(idempotency_key, gateway_customer_id) -> ChargeResult | None`: the payment an
    attempt made, looked up by its key, so an unknown outcome is read, never repeated.
  - `restore_transfer(charge_id, amount_pence, *, idempotency_key) -> TransferResult` (new model):
    give a provider back what a failed refund's transfer reversal took.
  - `ChargeResult.failure_code: str | None = None`: the decline or gateway code; codes starting
    `platform:` mean the problem isn't the customer's card.
  The fake implements all of them. The positional signature of `charge_visit` is unchanged.
- Why: exact, idempotent refunds; the admin retry (Stripe replays a declined attempt's result
  for 24 hours, so a retry needs a new key after cancelling the old attempt); not telling a
  customer to check their card when the provider's account is the problem.
- Workaround now: none needed; done in L3's adapter.
- Breaking? No. L1 and L2 code written against the F interface keeps working.

## Use `app.payments.charging.charge_visit` to charge (L2 finish, L1 tips)
- What: L2's `POST /api/p/visits/{id}/finish` and L1's tip charge call
  `await app.payments.charging.charge_visit(db, settings, gateway, visit_id, purpose=...)` after
  saving the visit, rather than calling `PaymentGateway.charge_visit` and writing the result
  themselves.
- Why: it does the intent, call and result in the order CLAUDE.md requires, records the ledger
  entry and messages exactly once with idempotency keys the Stripe webhooks share
  (`charge:<visit>:visit:paid:<template>`, `<attempt key>:<status>:<template>`), and is
  idempotent and resumable. Written separately, a webhook arriving between the call and the
  record could send `visit_done_customer` twice.
- Workaround now: L3's webhooks, retry and settle task use it; nothing in L1/L2 yet.
- Breaking? No. Integration may move it to `app/services/` if preferred.

## Register the payments collections
- What: add `PaymentEvents`, `PaymentRefunds` and `ChargeAttempts` (`app/repos/payments.py`,

- Breaking? No.

## Outbox search order (F's `GET /api/admin/outbox`)
- What: `Outbox.search` sorts and pages by `_id`, which follows time for new messages but not for
  seeded ones (their ids come from a hash), so the admin outbox shows the seed out of order. Sort
  by `(created_at desc, _id desc)` with a compound cursor.
- Why: the full outbox view (L3) reads as a timeline.
- Workaround now: none; new messages are in order.
- Breaking? No.

## A shared helper for cumulative refund splits
- What: `money.refund_split_after(original, already_refunded, amount)` in `app/core/money.py`,
  returning `refund_split(original, already + amount) - refund_split(original, already)`.
- Why: several partial refunds of one charge must add up exactly; L3 computes this today in
  `app.payments.refunds.refund_split_for` as the difference of two `money.refund_split` calls.
- Workaround now: that function.
- Breaking? No.
