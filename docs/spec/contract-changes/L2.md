## One charging path for finishing a visit (app/payments/charging.py, app/admin/tasks.py: L3's)
- What: L2's finish saves the finished visit (the calibration data and the day's mileage) in
  one transaction, then calls `app.payments.charging.charge_visit`. L2's own gateway call,
  ledger entry and messages, its resume task (`provider_resume_charges`) and
  `Charge.attempted_at` are gone. Added to app.payments, following its patterns, only what L3's
  path didn't do yet:
  1. `charging.start_unstarted`: a finished visit whose charge never started (the request
     stopped between saving the visit and `charge_visit` recording its intent) is started, with
     its normal first-attempt key. L3's `settle_pending_payments` task calls it first (one line
     in app/admin/tasks.py), after that task's 5-minute grace, oldest first in batches of 50 and
     however old (Codex review: a 7-day look-back could leave finished work unpaid for good;
     the look-back is there to stop repeated attempts before Stripe forgets a key, and this is a
     first attempt). Two starts at once are refused by `charge_visit`'s guarded intent (409,
     ignored), so it's charged once. Pending charges stay with `settle_unknown`, unchanged.
     Finishing the visit again also starts it (`charge_visit` is idempotent).
  2. In `apply_result`'s success branch (the one transaction that records every successful
     visit charge: the finish, a webhook, the settle task or an admin retry), a one-off booking
     becomes `completed` (state-machines.md: "a one-off's visit is finished and charged") and
     `notices.charged` sends `limit_reached` when the payment takes the provider to their
     earnings limit (once per period and amount). Both used to happen only in L2's finish, so a
     payment confirmed later (3-D Secure, a retry) skipped them.
- Why: brief 2a. One path, so webhooks, retries and the settle task never race two
  implementations.
- Writers: `bookings` is now also written by `app.payments.charging` (status `completed`);
  domain.md's writers line for bookings should say so.
- Breaking? No. (`tests/provider/test_finish.py`: `test_a_charge_that_never_started_is_started_once`,
  `test_finishing_again_starts_a_charge_that_never_started`,
  `test_a_payment_that_lands_later_completes_the_one_off_and_counts_to_the_limit`.)
- **Status (session S): resolved.** Accepted as made; domain.md's bookings writers now name `app.payments.charging` (`09a079a`).

## Renewals and L3's document checks (app/repos/providers.py: L2's, called by L3)
- What: `Providers.set_document` (L3's verify and reject write through it, inside their
  transactions) now records a verdict on the one copy L3 read, found by its file. A verified
  copy also supersedes the type's other checked or rejected copies (a checked renewal replaces
  the old copy) but never a newer upload still waiting; a rejected one replaces only itself, so
  rejecting a renewal leaves the verified copy counting. Waiting copies come first (L3's
  `doc_of` checks the first of a type), then the one that counts. If the copy L3 read has been
  replaced since (the provider uploaded again in between), it refuses with 409
  `document_changed`, which undoes L3's transaction. L2 stores a new upload first, and the
  provider's documents show a rejected renewal with its reason (`RenewalOut.note`) and let them
  upload again.
- Why: checked at the rebase: verifying re-verified the old copy and silently dropped the
  renewal; Codex review: rejecting a renewal deleted the valid copy; Codex re-check: a verdict on
  an upload replaced in the meantime deleted the valid copy and the newer upload.
- Breaking? No for L3's code: a verify, and a reject of a document's only copy, behave as before;
  the new 409 only happens in that race. (`test_documents.py`:
  `test_an_admin_checking_a_renewal_checks_the_upload_not_the_old_copy`,
  `test_rejecting_a_renewal_keeps_the_current_copy_counting`,
  `test_rejecting_the_only_copy_still_replaces_it`,
  `test_a_verdict_on_a_replaced_upload_changes_nothing`,
  `test_rejecting_the_current_copy_keeps_a_renewal_waiting`.) A repo raising an HTTP error is
  new: it's the only way to refuse inside L3's transaction without editing L3's code.
- **Status (session S): resolved.** The repository no longer raises an HTTP error: `set_document` raises the domain `Conflict`, mapped to the same 409 (A18, `505548c`).
