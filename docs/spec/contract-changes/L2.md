# Contract-change requests from L2

See README.md for the format. Each is for integration (I) unless it names another lane.

## The F contract test can't pass once a lane builds its endpoints
- What: `api/tests/shared/test_contracts.py` asserted every lane endpoint is a 501 stub (and that
  `GET /api/p/signup` answers 501 over HTTP). **I edited it (deviation, F-owned file):** the 501
  check now runs only on routes whose body still calls `not_implemented(` (`is_stub`), every lane
  route keeps the ownership and tagging checks, and the over-HTTP check calls an admin stub as an
  admin, skipping once none is left. Nothing else in the file changed.
- Why: `make test` must pass, and the test as written fails by design as soon as L2 implements.
- Workaround now: the edit itself. It follows each lane's progress without a per-lane list, so L1
  and L3 need no change of their own; if they edited it differently, I keep one version at rebase.
- Breaking? No.

## Re-seeding leaves money records from demo runs behind (app/seed/cleanup.py)
- What: `clear_children_of_bookings` deletes visits under a cleared booking but not their
  `ledger_entries`, `mileage_logs` (whose `visit_ids` point at them), ratings or files. Time off
  booked by seeded providers, and the cover requests it made, also survive `make seed`, so a second
  demo run finds the week already booked off. Please delete ledger entries and mileage logs for the
  cleared visits, and `time_off` plus cover `job_requests` (`cover_for_visit_id` on a cleared or
  seeded visit) for seeded providers.
- Why: after a demo finish and `make seed`, the tax pack and earnings still include the orphaned
  £31 charge, and the next acceptance walk fails on "You've already got time off booked".
- Workaround now: none in code (F's file). The tax pack copes with a ledger entry whose visit has
  gone (blank job name).
- Breaking? No.

## Marking messages read (app/repos/messages.py)
- What: a `Messages.mark_read(thread_id, user_id, *, session=None)` repo function (add the user to
  `read_by` on the thread's messages).
- Why: the provider's thread list and the Jobs tab show unread counts.
- Workaround now: `app/provider/threads.py` works unread out without writing: messages from others
  since the provider last wrote, unless already in `read_by`.
- Breaking? No.

## Counter bounds as a function (app/services/marketplace.py)
- What: `marketplace.counter_bounds(guide_pence) -> (lo, hi)`, used by `make_counter` itself.
- Why: the counter stepper and the counter preview need the same 80% to 300% whole-pound range.
- Workaround now: `app/provider/jobs.counter_bounds` mirrors the rule with Decimal half-up; for
  whole-pound guides it gives the same answer as `make_counter`'s `round()`.
- Breaking? No.

## A cover acceptance should check the visit is still scheduled (marketplace._cover)
- What: guard the visit update in `_cover` on `status: "scheduled"` as well as the cover state.
- Why: if the customer skips that visit (L1) while its cover request is open, someone could still
  "take" a skipped visit.
- Workaround now: L2 expires cover requests the day before (`provider_cover_deadline` task), but
  a skip before then isn't seen by the request.
- Breaking? No.

## Helpers and the shared offer endpoints (app/shared/marketplace_routes.py)
- What: refuse helpers (`user.helper_of` set) on `POST /api/p/requests/{ref}/accept|counter`.
- Why: `current_provider` gives a helper their provider's context, so a helper can accept jobs or
  suggest prices on the provider's behalf. Every L2 endpoint that isn't about the round refuses
  helpers (`app/provider/acting.py`). This touches the auth model, so it's listed as an open
  question in the L2 report too.
- Workaround now: the provider app never shows jobs to helpers (403 on `/api/p/jobs`).
- Breaking? No.

## L1: cover requests aren't the customer's requests
- What: `GET /api/c/requests` (and anything listing a customer's requests) should leave out
  requests with `cover_for_visit_id` set.
- Why: L2 creates a cover request (R23a) with the visit's `customer_id`; it isn't something the
  customer asked for, and they're told by `cover_coming` when someone takes it.
- Workaround now: none needed in L2.
- Breaking? No.

## L3: verifying renewals and helpers' documents
- What: (1) a provider may hold a verified, in-date document **and** a pending renewal of the same
  type (an upload made before the old one runs out, so they keep working). Verification of that
  type should use the **pending** entry's file and dates; `Providers.set_document` then replaces
  both. (2) A helper's documents are on `providers.helpers[].documents`, uploaded through
  `POST /api/p/documents` while signed in as the helper; the helper's status goes invited ->
  checking on their first upload. Admins need to verify those and set the helper `ready`.
- Why: A3 renewals (Lorna's DBS in the reminder window) and helpers' checks.
- Workaround now: none in L3's code; I'll check L3's verify endpoint when I rebase.
- Breaking? No (fields are additive: `Helper.documents`, default empty).

## Templates registered from L2 (app/provider/templates.py)
- What: fold `visit_done_customer_no_photo` and `cover_not_found` into the catalogue and
  regenerate notifications.md (`make docs`).
- Why: `visit_done_customer` says "added an after photo", untrue when there isn't one; and nobody
  is told when a cover request finds no one (state-machines.md: "the visit is skipped and the
  customer told").
- Breaking? No.

## Additive API and model changes (regenerate api.md and domain.md)
- New endpoints: `GET /api/p/requests/{ref}/counter-preview`, `GET /api/p/limit/preview`,
  `GET /api/p/own-customers/preview` (so the web never works out a fee or first-visit price).
- New response fields on L2's own models (schemas.py); `SignupStart.address_id` (optional).
- Models: `Helper.documents`, `Provider.email` (contact email from sign-up; F's users aren't
  written), `Charge.attempted_at` (which request is sending a pending charge to the gateway).
- Breaking? No.
